Known Limitations

Everything on this page is a deliberate boundary of version 1.0, verified against the real Confluence Cloud API. We would rather you read it before buying than discover it afterwards.

What a blueprint does not copy

Confluence performs the page copy with its own server-side task. That task copies pages, their nesting, attachments, labels and content properties. It does not carry across:

Not copiedWhat happens instead
WhiteboardsThe blueprint's whiteboards are detected at capture time and listed in the fidelity report. They are not recreated in the new space.
DatabasesSame as whiteboards: detected, reported, not recreated.
FoldersDetected and reported; the pages inside a folder are copied, the folder itself is not.
Blog postsNot copied.
Page history and versionsThe copied pages start at version 1. The original history stays with the blueprint.
Space themes and look-and-feelNot copied.
Page-level restrictionsDeliberately not copied. See below.

The app shows this list in the blueprint gallery and again on the capture screen, before an administrator confirms a blueprint — not in a footnote afterwards.

Page restrictions are never copied, on purpose

Confluence's copy task can carry page-level restrictions across. The app switches that off and keeps it off. Copying restrictions would create invisible access rules in a brand new space that neither the requester nor the approver ever reviewed. Space-level access is copied, because that is the point of a blueprint, and it is visible and reviewable in the space's own settings.

Blueprint size limit

A blueprint is capped at 500 pages. The cap is enforced when the blueprint is captured, not when a space is provisioned, so an administrator learns about it immediately. Larger source spaces can still be used by pointing the blueprint at a subtree.

The app never deletes anything

By design there is no delete. If provisioning fails after the space was created, the app reports exactly which step failed and offers a retry from that step. It leaves the partially provisioned space in place for an administrator to inspect and remove manually. The app also never archives a space, never deletes a page and never removes a permission.

Drift is detected, not repaired

The weekly inventory tells you when a provisioned space no longer matches its blueprint: role assignments changed, labels changed, the owner changed, or the review date has passed. Version 1.0 reports these. It does not automatically put them back, because a safe repair needs a diff preview and an undo path, and both are planned for a later version.

Requests, not self-service

A requester cannot create a space directly through the app. Every request needs an administrator approval, or an auto-approval rule an administrator configured in advance. This is the product's purpose rather than a limitation, but it is worth stating plainly.

One inventory sweep a week

The inventory refreshes on a weekly schedule, in bounded chunks, and can be triggered manually from the admin console. It is not real-time. Space creation and deletion events update the inventory immediately; everything else is picked up by the next sweep or by "Re-check now" on an individual space.

The reason is the Confluence rate limit: an app shares one pool of 65,000 points per hour across every site it is installed on. Sweeping continuously would spend other customers' budget. On a very large site (several thousand spaces) a full sweep is spread across the week.

Plan and tenant requirements

The app uses Confluence's role-based space access when the site has it, which covers sites reporting ROLES or ROLES_TRANSITION — that is every Standard, Premium and Enterprise site as the roles rollout completes. On a site without role-based access the app falls back to the legacy space-creation path; that path creates the space but cannot copy the blueprint's access configuration, so access must be set manually afterwards. The app tells you when it is in that mode instead of failing silently.

No JSM or Jira entry point yet

Version 1.0 has no web-trigger endpoint, so a Jira Service Management ticket cannot start a provisioning run. This is deferred deliberately: a web trigger would disqualify the app from Atlassian's "Runs on Atlassian" programme, which is verified and confirmed — the app's own eligibility check reports a web trigger as data egress. The integration is planned for a version where that trade-off can be made explicit.

Attachment listing

The app does not request permission to read attachments. Attachments inside a blueprint are copied by Confluence's task, but the app cannot show you an attachment inventory. This keeps the permission set smaller than the feature would be worth.

Notifications

Version 1.0 notifies inside the app: a requester sees their request status, an approver sees the queue. There is no email notification and no Confluence notification, because Forge offers no supported way to send one for this kind of event.

Browser support

The interface uses Atlassian's own design system and runs wherever Confluence Cloud runs. There is no separate mobile app; the admin console is built for a desktop-width screen.
