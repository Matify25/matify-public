Data security and privacy statement — Config Undo for Jira

Publisher: Matify · App: Config Undo for Jira (Jira Cloud) · Contact: support@matifyapps.de · Last updated: 7 October 2026

1. Overview

Config Undo for Jira records changes to Jira configuration and lets Jira administrators restore an earlier version of a configuration object after a preview and an approval. It is an Atlassian Forge app. This statement explains, technically and plainly, what the app processes, where it keeps it, and how it is protected. The formal policy is the privacy policy.

2. Hosting and architecture

  • Built on Atlassian Forge only: the app's functions run on Atlassian-hosted compute, and its data lives in Forge hosted storage (custom entities and the key-value store).
  • No Forge remote, no external backend, no web triggers. Matify operates no server, database or service the app depends on.
  • The admin interface is a Forge Custom UI page inside Jira's admin settings. All scripts, styles, fonts and icons come from the app's own bundle under Forge's default content security policy.
  • Long-running work (onboarding, re-reads, longer restores) runs in Forge queues; scheduled work runs on Forge scheduled triggers (hourly, daily, weekly).

3. Data we process

  • Jira configuration of eight types: permission schemes, notification schemes, workflows, workflow schemes, screens, custom-field options, field schemes and project settings (details, scheme associations, role actors, components, versions).
  • Jira audit-log records and workflow history, to know who changed what and when.
  • Admin input in the app: restore reasons, review notes, restore point labels, settings, approvals.
  • Display names of people, looked up from Jira when a page is shown, and kept only in the browser session.
  • Names of project roles and groups (not personal data), looked up from Jira and cached by the app for readable diffs; stored configuration keeps the ids.

The app does not read or store issues, comments or attachments.

4. Personal data

The app stores Atlassian account ids for longer than 24 hours:

  • inside stored configuration: user grants, user notification recipients, project leads, component leads, project role actors, user ids inside workflow rules;
  • in its own records: audit-log authors and account ids inside change summaries (change journal), restore requesters and approvers, admins who reject, cancel or retry a request, reviewers, restore point creators, the admin who last changed the settings, ledger actors.

It also stores free text admins type (reasons, notes, labels) and, only where an admin configured one as a notification recipient, an email address that is part of the notification scheme. It stores no display names, avatars or other profile data.

5. Data storage

All stored data is in Forge hosted storage on Atlassian's infrastructure. Configuration versions are stored once per distinct content (content-hashed, compressed); metadata (journal, versions, restore points, requests, ledger) is in Forge custom entities.

6. Tenant isolation

Forge hosted storage is partitioned per installation by the platform. The app uses no global or shared storage across customers, keeps no state between invocations outside that storage, and its logs contain no identifiers of other installations.

7. Data residency

Forge hosted storage follows the Jira site's data residency and moves with the site. All stored data listed in sections 4 and 5 is in-scope end-user data held there. Forge application logs are operational data outside that scope and contain no personal data or configuration content.

8. External data egress

None. The app declares no external domains, no remote backend and no web triggers. It calls only Jira's REST APIs and Forge platform services. Exports are generated in the admin's browser and saved locally.

9. External services and subprocessors

None besides Atlassian (hosting, storage, the Forge platform). No analytics, telemetry, error reporting, email or content delivery service is used.

10. Permissions and scopes

Six classic scopes: read:jira-work, manage:jira-configuration, manage:jira-project, read:jira-user, storage:app, report:personal-data. With the two manage scopes Jira grants the app user Jira-admin-equivalent permissions (verified: Administer Jira, Administer projects, Bulk change). Each scope is explained in Permissions and security.

11. Read/write model

  • Reads: configuration, the audit log and workflow history are read as the app; the administrator check and display names as the signed-in user.
  • Writes to Jira happen only for an approved restore of a configuration type an administrator enabled (off by default), with the kill switch off and the licence active — plus the guided safe test's own "Config Undo test" permission scheme, which the app creates, restores and deletes. The guided test's self-approval is bound on the server to the test scheme the current test created and is refused if that scheme was added to a project; the kill switch and the licence apply to it too.
  • The kill switch blocks every write. A running restore stops before its next write step; what was already written is verified and recorded (not rolled back).
  • Every restore is previewed, approved (four-eyes by default), checked against the live object at approval and before the first write, verified afterwards and recorded in a hash-chained ledger. Approve, reject and cancel are mutually exclusive per request. The live state is saved before every restore.
  • Restores that fit into one request run as the approving administrator (Jira's audit log names that person); longer restores run in the background as the app after re-checking the approver's Administer Jira permission. A restore that can't finish within the approval request continues in the background as the app, and the ledger records the switch.
  • The app never deletes customer schemes, workflows, screens, fields or projects.

12. Data retention

  • Retention period: 13 months by default, configurable from 3 to 36 months; a weekly job applies it.
  • Versions and journal entries older than the retention period are deleted. Kept regardless: the latest version of every object, the version that was current at the retention boundary, versions in pinned restore points and versions of unfinished restore requests.
  • Restore points older than the retention period are deleted unless pinned. Finished restore requests older than the retention period are deleted with their preview and result; previews that were never submitted are deleted after 24 hours.
  • The ledger is kept for the life of the installation.

13. Data deletion

  • Delete all app data (Settings → Danger zone, typed confirmation) deletes all stored versions, journal entries, restore points, restore requests, ledger entries and other app keys.
  • Data the app deletes is removed from its storage at once; Atlassian may keep a deleted copy for a limited time for recovery, under its own Forge data retention.
  • On uninstall the app writes a final UNINSTALL ledger entry; stored data then is retained and deleted per Atlassian's Forge data retention for uninstalled apps.
  • Excluded objects and projects stop being recorded; their history ages out with retention (each object's latest version is kept).

14. Personal data requests

The app reports the account ids it stores to Atlassian every week through the Forge personal data reporting API. For a closed account it replaces the account id with a random closed-account: token in journal entries (authors, reviewers, change summaries), restore requests with their stored preview and result, restore points, stored configuration versions and the settings' last editor. It re-hashes the affected versions and deletes the old copies, removes the account id and token mapping from the ledger (the chain stays verifiable), deletes the cached administrator check for that account and records a count-only TOMBSTONE entry. Free text typed by administrators is not scanned. This runs even when the licence has lapsed. Other requests: support@matifyapps.de.

15. Logging

Forge logs contain event names, counts, durations, error codes and a random correlation reference. One warning event contains the numeric id of a configuration object Jira refused to show to the app. No account ids, names, email addresses, free text or configuration content are logged.

16. Transport and platform security

All traffic between the app, Jira and the browser runs inside Atlassian's platform (Forge functions call Jira through the Forge runtime; the Custom UI talks to the app's functions through the Forge bridge). Storage, transport encryption and infrastructure security are Atlassian's; see Atlassian's own Forge and cloud security documentation. Matify adds:

  • a server-side Administer Jira check on every request,
  • strict schema validation of every request payload, and encoding of identifiers in Jira API paths,
  • no collected credentials, tokens or secrets,
  • CSV exports safe against formula injection, and text rendered as text in the interface,
  • a release process that builds one tagged Forge build only after automated gates pass (the manifest has no egress, remote or web trigger and exactly the six scopes listed; lint; type checks; all tests; the interface build) and deploys that same build to staging and production,
  • pinned dependencies with lockfiles; npm audit at the security review of the initial release (2026-10-06) found no known vulnerabilities.

No compliance certification (such as SOC 2 or ISO 27001) is claimed for the app or for Matify.
