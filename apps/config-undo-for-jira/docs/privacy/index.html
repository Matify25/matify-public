Privacy and data

What Config Undo stores

DataContains personal data?
Versions of permission schemes, notification schemes, workflows, workflow schemes, screens, field options, field schemes and project settingsYes: Atlassian account ids of users named in the configuration (user grants, user notification recipients, project and component leads, role actors, user ids inside workflow rules). An email address is stored only where an admin configured it as a notification recipient.
Change journal: time, type, object, change summary, source, review statusYes: the author's account id (from Jira's audit log), the reviewer's account id and note; a change summary can contain the account ids of users added to or removed from the configuration
Restore pointsYes: the creator's account id
Restore requests: preview, plan, resultYes: requester and approver account ids and the reason they typed; the preview and result can contain account ids from the configuration
LedgerYes: an account id per entry, kept outside the hashed part, plus a random per-person token inside it
SettingsYes: the account id of the admin who last changed them
Names of project roles and groups, cached for displayNo (role and group names are not personal data)
Progress, rate-limit counters, locks, licence statusNo
A list of the account ids stored, for Atlassian's personal data reportingYes (account ids only)

Not stored: names of people, avatars, user email addresses (other than notification recipients an admin configured), issues, comments, attachments, credentials, tokens. People's names you see in the app are looked up from Jira when the page is shown and kept only in your browser session. Names of project roles and groups are looked up from Jira and cached by the app so that diffs read "Project role: Developers"; the stored versions keep the ids.

Free text that admins type (reasons, review notes, restore point labels) is stored as typed. Don't put personal data in it that you don't want stored.

Where it is stored

Only in Forge hosted storage (custom entities and the key-value store) on Atlassian's infrastructure, separate for each installation.

  • Data residency: Forge hosted storage follows your Jira site's data residency and moves with it. Everything listed above is in-scope end-user data stored there.
  • Out of scope for residency: Forge application logs. They contain no account ids, names, free text or configuration content (event names, counts, error codes, references, and in one warning the numeric id of a configuration object Jira refused to show).
  • No egress: nothing is sent outside Atlassian. There are no external services, analytics or subprocessors besides Atlassian.

How long it is kept

A weekly maintenance run applies the retention period you set in Settings (13 months by default, 3–36 months).

DataKept for
Configuration versionsuntil they are older than the retention period, except the versions below
The latest version of every objectalways
The version that was live at the retention boundary (the newest one captured before it)kept, so a change to an object that stayed unchanged for longer than the retention period can still be undone
Versions referenced by a pinned restore point or by a restore request that hasn't finisheduntil unpinned / finished
Journal entriesuntil they are older than the retention period
Restore pointsuntil they are older than the retention period, unless pinned
Finished restore requests with their preview and resultuntil they are older than the retention period
Previews that were never submitted24 hours
Ledgerfor the life of the installation (append-only)
The list of stored account idsuntil the account is erased or all app data is deleted

Reducing retention asks for confirmation and shows an approximate count of the stored versions older than the new period. The count includes versions that are kept anyway (each object's latest version, the boundary version and pinned ones).

Deleting data

  • Delete all app data: Settings → Danger zone. Type DELETE ALL CONFIG UNDO DATA. Config Undo first offers journal and ledger exports, then deletes every version, journal entry, restore point, restore request and ledger entry, and all of its other stored keys, in the background. A final record goes to the Forge log, not to storage. Recording stays paused afterwards until you resume onboarding in Coverage & Health or install the app again.
  • Retention: lower the retention period in Settings.
  • Exclusions: excluded objects and projects are no longer recorded. Their existing history ages out with retention like any other history; each object's latest version is kept.

Data the app deletes is gone from the app's storage at once. Atlassian may keep a deleted copy for a limited time so it can recover from accidental deletion, as described in Atlassian's Forge documentation on the hosted storage data lifecycle.

Closed Atlassian accounts (personal data reporting)

Config Undo reports the account ids it stores to Atlassian every week through the Forge personal data reporting API. This covers every account id the app keeps: in configuration versions, change authors and account ids inside change summaries, reviewers, restore requesters and approvers, admins who rejected, cancelled or retried a request, restore point creators and admins who changed settings.

When Atlassian reports an account as closed, Config Undo:

  1. replaces that account id with closed-account: followed by a random token that is not derived from the account id, in the journal (authors, reviewers and change summaries), restore requests (requesters and approvers) and their stored preview and result, restore points (creators), stored configuration versions and the settings' last editor,
  2. recalculates the affected versions and the references to them, and deletes the old copies of those versions,
  3. deletes the account id and the person's token mapping from the ledger, so the ledger chain still verifies,
  4. deletes the cached administrator check for that account,
  5. writes a TOMBSTONE ledger entry with counts only.

Free text that admins typed (reasons, review notes, labels) is not searched for account ids.

Restores skip account holders that no longer exist, and the preview lists them.

This weekly run continues even if the licence lapses, because the duty to erase closed accounts doesn't end with the subscription.

Uninstalling

Before the uninstall completes, Config Undo writes an UNINSTALL ledger entry. Its stored data stays in Forge hosted storage and is retained and deleted per Atlassian's Forge data retention for uninstalled apps. If you reinstall while that data is still retained, Config Undo continues with it: the journal, versions, restore points and ledger are still there, and onboarding resumes or runs again to catch up. After Delete all app data, a reinstall starts with empty storage. Nothing is exported or sent anywhere on uninstall, so export first what you want to keep, or use Delete all app data before uninstalling.

Exports

Exports (journal CSV/JSON, review report, ledger CSV/JSON, single versions as JSON) are built in your browser and saved on your computer. They include account ids, and the journal and review exports add display names at the time of export. Handle them like any other admin data.
