Permissions and security

The six permissions (scopes), in plain words

ScopeWhat Config Undo uses it forRead / write
read:jira-workRead permission schemes; check that the person using the app holds Administer Jiraread
manage:jira-configurationRead the audit log, workflow history, workflows, workflow and notification schemes, custom field contexts and options, field schemes. Write schemes, workflows and options only for an approved restoreread + write
manage:jira-projectWrite project settings (details, scheme associations, role actors, components, versions) and screens only for an approved restorewrite
read:jira-userShow people's names in the app when you view a page, and the author filter; show group names in diffs. People's names are never storedread
storage:appStore versions, the journal, restore points, requests and the ledger in Forge hosted storage on your siteapp storage
report:personal-dataReport stored account ids to Atlassian weekly so closed accounts are erased—

There is no narrower classic scope that lets an app read the audit log, workflows, notification schemes or field contexts, and Jira has no granular scope for notification-scheme writes. Config Undo doesn't ask for issue writes (write:jira-work), webhooks, Confluence or any external access.

What the app user can do — stated plainly

Because of manage:jira-configuration and manage:jira-project, Jira gives the Config Undo app user Jira-admin-equivalent permissions. In our capability test it held Administer Jira, Administer projects and Bulk change. Jira's global permission settings can't narrow this.

Config Undo itself writes to your Jira configuration only when all of these hold:

  • a Jira admin turned on restore for that configuration type (off by default),
  • an admin previewed the restore and submitted it with a reason,
  • the request was approved (by a second Jira admin by default), the approval window hasn't passed and the live object still matches the preview,
  • the kill switch ("Disable all restores") is off and the licence is active.

The guided safe test is the only case with fewer conditions: on your request it creates a permission scheme named "Config Undo test …" that no project uses, restores it after you changed it, and deletes it again. Its restore doesn't need restore to be enabled for permission schemes or a second approver. That exception applies only to the test scheme the current test created, which the server checks before every step, and the test refuses to restore the scheme if it has been added to a project. The kill switch and the licence apply to the guided test like to every other write.

Config Undo never deletes your schemes, workflows, screens, fields or projects. In restores it disables options and archives versions instead of deleting them, and lists components for manual removal.

Who can use the app

Only users with the Administer Jira global permission. Every request from the app's pages is checked on the server: the app asks Jira whether the calling user holds Administer Jira (cached for at most five minutes) before it returns any data or does anything. Menu visibility is only a convenience, never the security boundary.

Restore-specific rules, all enforced on the server:

  • four-eyes approval by default: the requester can't approve their own request;
  • single-admin mode requires typing the object's exact name;
  • exactly one decision per request: approve, reject and cancel exclude each other, and a rejection that arrives while an approval is running wins;
  • approval expires (24 hours by default);
  • the live object is re-read at approval and again right before the first write; any change stops the restore;
  • one restore per object at a time (lock);
  • every request, approval, execution, result and settings change is written to the hash-chained ledger.

Four-eyes approval protects against mistakes. It is not a control against a malicious administrator: any Jira admin can switch to single-admin mode or delete all app data. Both need an explicit confirmation and are recorded in the ledger (Delete all app data removes the ledger too, so export it first if you need it as evidence).

The preview tells you in advance when a restore is estimated to run in the background. The guided safe test creates and deletes its test scheme as the app.

Reads of your configuration (recording, previews, compare with live) are made as the app.

Platform and architecture

  • Forge only. Config Undo runs on Atlassian Forge: Atlassian-hosted functions and Forge hosted storage. Matify runs no servers and no database, and has no access to your data.
  • No egress. The app declares no external domains, no remote backend and no web triggers. It talks only to Jira's REST APIs and Forge services. The admin interface loads everything from its own bundle under Forge's default content security policy.
  • Tenant isolation. Forge hosted storage is separate per installation; the app keeps no state between invocations except in that storage.
  • Data residency. Stored data lives in Forge hosted storage, which follows your Jira site's data residency.
  • Runs on Atlassian. Atlassian's deployment check reported the production version 2.0.0 eligible for the Runs on Atlassian program. The badge itself is granted and shown by Atlassian on the Marketplace listing.

Application security

  • Every request payload is validated on the server against a strict schema (allowed values, patterns for object keys and ids, length limits). Identifiers are encoded before they are put into a Jira API path.
  • Text you type (reasons, notes, labels) is shown as text, never as HTML. CSV exports neutralise cells that a spreadsheet would run as a formula.
  • Restore plans are validated before they run (for workflows by Jira's own validation endpoint). A write whose outcome is unknown is never repeated blindly; the app re-reads and reports instead.
  • No credentials, API tokens or secrets are collected or stored. Authentication is Forge's own.
  • Forge logs contain event names, counts, error codes and a correlation reference. No account ids, names, email addresses, free text or configuration content are logged.
  • Dependencies are pinned with lockfiles. An automated dependency scan (npm audit) found no known vulnerabilities at the security review of the first release.
  • Every release is built once: an automated gate checks that the manifest has no web trigger, external egress or remote and exactly the six scopes above, then lint, type checks, all tests and the interface build must pass. That single tagged build is deployed unchanged to staging and then to production.

No compliance certification (such as SOC 2 or ISO 27001) is claimed for Config Undo or Matify.
