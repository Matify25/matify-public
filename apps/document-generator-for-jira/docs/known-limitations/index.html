Known limitations

Version 1.0.0. We list what Document Generator does not do, or does only partly, so that nobody finds out in front of a stakeholder.

Browsers

  • Safari has not been verified. Downloads were verified in Chrome on a real Jira site, and in Edge and Firefox in a test setup that uses the same browser sandbox as Jira. If a download does not start in Safari, use Attach to … and open the document from the work item, or use Chrome, Edge or Firefox.
  • Background documents are rendered in the browser and need a current Chrome, Edge or Firefox.
  • Documents are built on the browser's main thread. While the Word document is filled and while PDF pages are laid out, the page can pause briefly (about half a second per 1,000 work items in our tests).

PDF output

PDF is made by Matify's own converter from the filled Word document and reproduces a documented subset of Word — see the PDF fidelity statement. DOCX is the format for the exact layout. In particular:

  • A heading can end alone at the bottom of a page — there is no "keep with next".
  • JPEG orientation (EXIF) is ignored, so a photo taken in portrait mode can appear rotated.
  • Fonts: PDF text is set in Noto Sans and Noto Sans Mono, which cover Latin (with Latin Extended), Greek and Cyrillic. Chinese, Japanese, Korean, Arabic, Hebrew, Thai and Devanagari cannot be shown, and right-to-left layout is not supported. Some symbols are missing from the bundled font, for example "→". Missing characters are listed with the result. Use DOCX in these cases.
  • Template fonts (Calibri, Aptos, Arial …) are replaced, so line breaks and page counts can differ from Word.
  • Not reproduced: text boxes, floating pictures and shapes, SmartArt, charts, multiple columns, different first-page or odd/even headers, fields other than page numbers, tracked changes, Word comments, footnotes and endnotes, embedded fonts, equations, legacy shapes and watermarks, pictures that are not PNG or JPEG. The validator warns about each.
  • Word table styles are approximated (grid borders, bold header row); "Table Grid" and borders set directly are exact.
  • Row heights and vertical alignment in table cells are ignored; only the default header and footer are used; with several sections only the last section's page setup is used.
  • Numbered lists: PDF counts each Word list on its own. Word can continue numbering across separate lists that share a list definition; the PDF then restarts.
  • PDF output is not tagged for accessibility (not PDF/UA) and not PDF/A.

Template language

  • Only the placeholders in the Template cookbook are supported. No expressions, scripting, arithmetic, else-if or and/or.
  • Not in this version: is:FIELD=VALUE conditions; grouping and count:FIELD=VALUE on fields other than work type, status, status category, fix versions and components; percent: on fields other than status category; change history in documents.
  • Word templates only: no Excel or PowerPoint templates, no PowerPoint output.
  • Work item tags outside {{#issues}} only show a value in single-item documents.
  • Status category names follow each user's Jira language; use the keys new, indeterminate and done in count: and percent: to be safe.
  • Month names in date:d MMM yyyy follow the browser's language data.
  • At most 500 placeholders per template, 5 MB per template file.
  • The Default date format setting applies to dates without a pattern of their own ({{duedate}}, {{doc.date}}, |date). Date-time placeholders without a format ({{created}}) and |datetime keep each user's Jira language style with the time; use a date pattern in the placeholder for a fixed format there.
  • Field codes built from other fields are not allowed in templates: a field whose code contains another field (for example { IF { MERGEFIELD … } … } or { = { PAGE } - 1 }), and QUOTE and SET fields (E-007).

Rich text and images

  • Rich-text images are embedded only when they are attachments of the same work item. External images, and images that can't be matched to an attachment, appear as "[image: …]".
  • Only PNG and JPEG are embedded; up to 5 MB each, 10 per work item, 200 and 100 MB per document. Other images appear as "[image: filename]".
  • Lists nested deeper than 3 levels are flattened to level 3.
  • Other apps' macros in rich text are left out or reduced to their text.
  • Only http, https and mailto links are kept as links.

Excel output

  • One sheet, one row per work item. Curated packs have fixed column sets; for your own templates the columns are derived from the template's work item placeholders. Columns can't be configured separately.
  • Rich text is exported as plain text; a cell holds at most 32,767 characters.

Scale

  • Up to 200 work items directly in the browser (50 with comments) and up to 1,000 work items in a background document, in every format. A higher limit for DOCX and XLSX is not available yet.
  • Comments: the most recent 10 per work item by default (up to 20), for at most 500 work items per document.
  • One background document collects at a time per site; up to 3 in progress per person and 10 per site.
  • Collected data of a background document: up to 50 MB, kept 24 hours after it is ready (or 24 hours after it failed, so it can be retried).
  • One work item whose content alone is larger than about 200 KB compressed (very long text or many long comments) can't be included in a background document: it is left out and listed as "too large" (DGJ-LIMIT-ITEM-SIZE). Generate it on its own or without comments.
  • When Jira's shared API limit for apps runs low, documents are limited or wait until the next full hour (Large sites).
  • Searches must have at least one condition (Jira does not allow apps to run unbounded searches).

Product scope

  • The issue navigator action uses an Atlassian module in preview. If it is unavailable on your site, Apps → Document Generator → New document offers the same flow with a JQL or saved filter.
  • Selecting rows in the issue navigator does not limit the document; Jira passes the search, not the selection, to apps. Refine the JQL instead. (Observed on a Jira Cloud site in October 2026: the bulk-selection bar offers no app actions, and Apps → Generate document… receives the search only.) If Jira passes a selection in the future, the app uses it.
  • Generated documents are not archived by the app. Download them or attach them to a work item.
  • No scheduled documents, e-mail delivery or Jira Automation actions.
  • No output to Confluence, SharePoint, Google Drive or other storage.
  • No customer-portal (Jira Service Management portal) entry point. In Jira Service Management, agents generate documents from the agent view (••• → Generate document on a request).
  • Data security policies: Jira hides work items that an Atlassian data security policy blocks for apps the same way as work items you can't see, and does not tell the app about work items a search leaves out for this reason. The app lists a work item as blocked by the policy only when Jira says so for that work item.
  • No e-signatures; sign-off lines in templates are plain text.
  • Template versions: the current and the previous version are kept (plus versions in use by background documents).
  • Not in this version: usage CSV export, a diagnostics download, bulk actions on templates, exporting all templates as one ZIP.
  • The app's pages are in English.
  • When the licence or trial ends, background documents that were ready can no longer be downloaded: their collected data is deleted and they have to be generated again after a renewal. Admin configuration is read-only until then; templates can still be downloaded (Admin guide).
  • Usage counters can rarely count one document too few when many documents complete at the same moment.
  • Jira Server and Data Center are not supported.
