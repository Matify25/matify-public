Permissions and security

Document Generator is an Atlassian Forge app. Its code runs on Atlassian's infrastructure, its data lives in Forge hosted storage, and it sends nothing outside Atlassian.

Scopes

The app requests five scopes — the classic Jira scopes it needs and two Forge platform scopes. No admin-level (manage:*) scopes, no Confluence or Service Management scopes.

ScopeWhy
read:jira-workEvery Jira read: searches, work items, comments, attachments and their content, fields, permissions, saved filters, projects, JQL checks and counts. It is the only scope that allows offline user impersonation, used only for background documents (see below).
read:jira-userThe generating person's language, time zone and groups (/myself), and the group picker in the admin settings.
write:jira-workExactly one action: attaching a generated document to a work item, when a user clicks Attach. The app never edits fields, comments or transitions and never deletes anything in Jira.
storage:appForge hosted storage for templates, settings, background documents and counters.
report:personal-dataAtlassian's personal data reporting for the account IDs the app stores (see Privacy and data).

Every read runs as a person

  • Documents generated now: the app's backend reads Jira as the signed-in user. Images and attach-back go through Atlassian's browser bridge, which always acts as the signed-in user.
  • Background documents: the background job reads Jira as the person who started the document, through Atlassian's offline user impersonation. The app never reads as anyone else.
  • No reads as the app itself. The app makes no Jira calls with its own app identity. It uses its app identity only for its own storage, the licence check and personal data reporting.

As a result, a document never contains work items, comments or images that the generating person can't see in Jira.

Safeguards around background documents

Offline impersonation is powerful, so it is fenced in:

  • The person a background document reads as is taken from the Jira session that started it. It is never accepted from a request, and it cannot be changed afterwards; every stored job record is signed, and a record whose owner does not match its signature is refused.
  • Impersonation happens in exactly one place in the code, only in the background job, and only for a job that is currently collecting or waiting for budget. Resolvers, the daily cleanup and the uninstall handler never impersonate.
  • Impersonation is limited to read:jira-work. It cannot write to Jira or read user profiles.
  • Jira applies the person's current permissions to every read. If their access changes, the next batch reflects it.
  • Only the person who started a background document can read its collected data. Jira admins can cancel or delete it, but not read it.

These rules are covered by automated contract tests.

App-level controls for admins

On top of Jira's permissions, Jira administrators decide:

  • who may generate documents (everyone with Browse permission, or members of selected groups);
  • which formats are allowed;
  • whether documents may be attached to work items, and whether comments may be included;
  • which templates exist, which projects each template is published to, and which packs are on;
  • lower limits and a lower API budget.

Admin functions require the Jira global permission Administer Jira. The app checks it on the server, as the user, for every admin action — hiding the admin pages from non-admins is only a convenience.

Template safety

Word files can contain active or remote content. The validator rejects templates with:

  • macros (VBA, macro-enabled files, ribbon or keyboard customisations);
  • encryption, password protection, write protection or enforced editing restrictions;
  • relationships to external content other than ordinary hyperlinks (for example linked pictures);
  • hyperlinks to files, network shares or programs (only http:, https:, mailto: and in-document links are allowed), and a hyperlink base that points to a file share;
  • mail-merge settings (a data source or SQL query Word would offer to run);
  • the field codes INCLUDEPICTURE, INCLUDETEXT, INCLUDE, LINK, DDE, DDEAUTO, IMPORT and DATABASE — also when the name is quoted or split within the field code;
  • field codes built from other fields: any field whose code contains another field, and QUOTE and SET fields in any form (plain REF, PAGEREF, PAGE, NUMPAGES and DATE fields stay allowed);
  • imported content chunks (altChunk), OLE objects and embedded packages (wherever they are stored in the file), ActiveX controls, sub-documents, frames and framesets, attached templates and XML document type declarations;
  • files that are too large, unpack too large or look like zip bombs — checked at upload and again each time a document is generated from the stored template.

The check reads every XML part of the file, whatever its name or location, the same way Word finds them. Details per item: E-007.

Output scan: the same check runs on every Word document the app fills — before it is downloaded or attached, and also on the Word document a PDF is made from. A document that fails is blocked. So a generated document cannot load remote content or prompt for DDE when it is opened.

Template content is never executed. The placeholder language has no expressions or scripting, and the engine contains no code evaluation (eval or similar) — this is checked automatically in every build.

Rich text and spreadsheets

  • Rich text is read from Jira's document format and mapped element by element to Word; it is never inserted into a web page and never executed. Values in the app's pages are displayed as text.
  • Only http, https and mailto links are kept as links.
  • Excel output: values that start with =, +, - or @ are written as text, so Excel never evaluates them as formulas.
  • File names are cleaned of path separators and control characters and limited to 120 characters.

No external connections

  • The app declares no external domains, no remote backend and no web triggers.
  • Its pages load scripts, styles, fonts and icons only from the app's own bundle, under Forge's default content security policy; the app requests no CSP relaxations (no unsafe-eval, no unsafe-inline scripts).
  • Fonts for PDF output are bundled with the app.
  • Links to this documentation are opened by you, as normal browser navigations; the app does not fetch them.

Data isolation

Forge hosted storage is separate for every installation. The backend keeps no customer data in memory between invocations, and an installation cannot read another installation's data (covered by tests).

Engineering practices

  • Every backend call checks its input against a strict schema with size limits and returns errors without technical details; unexpected errors show a reference for support.
  • Library versions are pinned; dependencies are audited for known vulnerabilities before each release.
  • Security issues are handled according to Atlassian's Security Bug Fix Policy for Marketplace apps.

Reporting a security issue

Email support@matifyapps.de with "security" in the subject. Please do not post security issues in the public tracker.
