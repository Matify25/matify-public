Data security and privacy statement — Document Generator for Jira

Publisher: Matify · App: Document Generator for Jira (Word, PDF & Excel) (Jira Cloud) · Contact: support@matifyapps.de · Last updated: 20 October 2026

1. Overview

Document Generator turns Jira work items into Word, PDF and Excel documents from Word templates. Jira administrators upload and validate templates; users generate documents from a work item, a search or the app's Documents page, download them or attach them to a work item. It is an Atlassian Forge app. This statement explains what the app processes, where it keeps it and how it is protected. The formal policy is the privacy policy.

No Jira content or personal data leaves Atlassian. Matify sees only anonymous usage counts in Forge logs, and only if your admin allows app log access.

2. Hosting and architecture

  • Built on Atlassian Forge only: the backend is executed by Atlassian-hosted compute, and the app's data lives in Forge hosted storage (custom entities and the key-value store).
  • No Forge remote, no external backend, no web triggers. Matify operates no server, database or service the app depends on.
  • Documents are built in the user's browser inside the app's Forge page, with libraries and fonts bundled with the app. Generated documents are saved on the user's device; the app does not store them.
  • Large documents collect their data in a Forge queue on Atlassian's infrastructure, one at a time per site. A daily Forge trigger runs retention cleanup and personal data reporting.

3. Data we process

  • Jira data, read with the generating person's permissions: the work item fields a template uses, rich text, comments when the person opts in, linked work items, sub-tasks and child work items, attachment names and sizes, and the contents of PNG and JPEG attachments placed in a document. Also the person's language, time zone, groups and Jira permissions, and the site's field list.
  • Templates that Jira administrators upload (Word files with any content they contain), with their placeholder lists and validation reports.
  • Settings, background document records and anonymous usage counters.

The app reads only the fields a template uses, never all fields.

4. Personal data

Stored for longer than 24 hours: the Atlassian account ID of each person who starts a background document, kept with that document's record (deleted 30 days after the document ended). The collected data of a background document — which can contain people's display names, the account IDs of people @mentioned in rich text or comments, and other content from Jira — is kept 24 hours after it is ready, or 24 hours after the document failed (so that it can be retried). Templates can contain whatever personal data administrators put into them.

The app stores no e-mail addresses, avatars, passwords or API tokens.

Generated documents contain the Jira data their template selects and can contain the name of the person who generated them; they are created on that person's device and are under your organisation's control.

6. Tenant isolation

Forge hosted storage is partitioned per installation by the platform. The backend keeps no customer data in memory between invocations, and the app's tests check that one installation never sees another installation's data.

7. Data residency

Forge hosted storage is data-residency enabled and follows your Jira site's location. In scope: templates and their versions, placeholder lists and validation reports, background document records and collected data, settings. Out of scope: usage counters and API budget records (no end-user data) and anonymous log lines. Attachments created by the app's users are Jira data under your site's own residency.

8. External data egress

None. The app declares no external domains, no remote backend and no web triggers. It calls only your Jira site's REST API and Forge platform services (storage, queue, personal data reporting, licence). Its pages load no external scripts, styles, fonts or images and request no relaxation of Forge's default content security policy. The bundled Atlassian Design System libraries contain a dormant feature-flag client with built-in host names of Atlassian's flag service; the app never configures or starts it, declares no egress for it, and Forge's default content security policy would block any such connection.

9. Subprocessors

Atlassian only (Jira, the Forge platform). No analytics, telemetry, error-reporting, e-mail or content delivery service.

10. Permissions and scopes

Five scopes: read:jira-work, read:jira-user, write:jira-work, storage:app, report:personal-data. No manage:* (admin-level) scopes. write:jira-work is used for exactly one action: attaching a generated document to a work item when a user clicks Attach. Each scope is explained in Permissions and security.

11. Read/write model

  • Every Jira read runs as a person. Documents generated now read as the signed-in user; background documents read as the person who started them, through Atlassian's offline user impersonation; the app never reads as anyone else. The app makes no Jira calls with its own identity.
  • Impersonation is limited to read:jira-work, happens in one place in the code, only for a background document that is collecting, and only for the owner recorded — and signed — when the document was started. Contract tests cover these rules.
  • One write: attaching a document, on a click, as the clicking user, never replacing or deleting anything. The app never edits fields, comments or statuses.

12. Access control

  • Administrator functions require the Jira global permission Administer Jira, checked on the server, as the user, for every action.
  • Administrators can limit document generation to selected groups, switch formats and attaching off, publish templates per project and lower all limits.
  • Only the person who started a background document can read its collected data; administrators can cancel or delete it but not read it.
  • If a permission cannot be confirmed, access is refused.

13. Template and output safety

Templates are rejected when they contain macros, encryption or password protection, links to external content, links to files, network shares or programs (only web, e-mail and in-document links are allowed), a hyperlink base on a file share, mail-merge data sources, the field codes INCLUDEPICTURE, INCLUDETEXT, INCLUDE, LINK, DDE, DDEAUTO, IMPORT or DATABASE (also when the name is quoted or split within the field code), field codes built from other fields (any field whose code contains another field, and QUOTE and SET fields in any form), imported content chunks, OLE or ActiveX objects and embedded packages, sub-documents, frames, attached templates or XML document type declarations, or when they are oversized or look like zip bombs. The check reads every XML part of the file, whatever its name or location. Every filled Word document is scanned again before it can be downloaded or attached (including the one a PDF is made from), and the zip-bomb check runs again each time a document is generated from a stored template. Template content and rich text are never executed; Excel output is protected against formula injection; file names are sanitised.

14. Personal data reporting and deletion

  • Weekly personal data reporting through Atlassian's API for the stored account IDs, also when the subscription has ended. For closed accounts the app deletes their background document records and collected data.
  • Users can delete their own background documents' data at any time. Administrators can use Delete all app data (typed confirmation): it removes all templates, background documents and collected data, settings, usage counters, caches and API budget records, verifies that nothing is left, and only then reports that it has finished; while it runs, the app stores nothing new.
  • When the subscription ends: no new documents; queued background documents are cancelled and the collected data of ready ones is deleted; the administration pages become read-only; template download, template and background document deletion and Delete all app data stay available.
  • Uninstall: open background documents are cancelled and their collected data deleted; all other app data follows Atlassian's lifecycle for uninstalled Forge apps (retained 28 days, then deleted). Do not rely on a reinstallation to restore — or to remove — earlier data; download the templates you want to keep before uninstalling.

15. Logging

Logs contain event names, error codes, counts, durations and random reference numbers — no names, account IDs, e-mail addresses, work item keys, JQL or content. One anonymous line per completed document:

{"evt":"dgj.doc","fmt":"pdf","entry":"navigator","tpl":"pack:status-report","items":42,"ms":5300,"v":"1.0.0"}

Matify can see logs only as far as Atlassian makes them available to app developers; site administrators can turn off log access for the app.

16. Vulnerability management

Library versions are pinned and audited for known vulnerabilities; the build checks that no code evaluation (eval or similar) and no external connections exist. Security issues are handled under Atlassian's Security Bug Fix Policy for Marketplace apps. Report vulnerabilities to support@matifyapps.de with "security" in the subject — not in the public tracker.
