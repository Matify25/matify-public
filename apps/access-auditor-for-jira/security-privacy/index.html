Data Security and Privacy Statement

Product: Access Auditor for Jira Publisher: Matify Platform: Atlassian Forge, Jira Cloud Last updated: 2026-09-13

Every statement below describes the app as it ships. Nothing here describes a planned feature, and no security certification is claimed. Where a claim can be checked against the app's own published manifest, this document says how.

1. Overview

Access Auditor for Jira is a read-only auditing app for Jira Cloud. It reads your site's permission configuration — permission schemes, project roles, groups, shared filters and shared dashboards — resolves each grant to the people and groups who actually hold it, and reports configurations that are likely to be a risk.

Three properties define its security posture, and each is enforced by the Atlassian Forge platform rather than by the app's own discipline:

  • It runs entirely inside Atlassian's infrastructure.
  • It declares no ability to send data anywhere outside Atlassian.
  • It declares no ability to write anything to Jira.

It does store personal data, in the form of Atlassian account identifiers and display names. Section 4 says exactly what and why.

2. Hosting and architecture

Access Auditor is an Atlassian Forge app. Both its compute and its storage are hosted by Atlassian, inside your own Jira Cloud installation. Matify operates no server, no database and no endpoint that this app talks to.

ComponentWhere it runs
Backend functions and triggersAtlassian Forge, nodejs22.x runtime
Administration interfaceForge Custom UI, served from the app's own bundled resources
All app storageForge custom entity store and Forge key-value store

The Forge CLI reported the app eligible for Atlassian's Runs on Atlassian programme on each deployment, including the production deployment. That is Atlassian's tooling making the determination, not a self-assessment. The programme badge itself is granted by Atlassian on the listing, not by this document.

4. Personal data

Access Auditor stores personal data. Saying otherwise would be false.

An Atlassian account identifier (accountId) is personal data under Atlassian's own definition, and the app cannot do its job without one: an access review that cannot name who holds a permission is not an access review.

Personal data storedWhy it is necessary
Atlassian account identifierIdentifies the holder of a permission, and links a finding to the account it concerns
Display nameSo an administrator reading the audit sees a person rather than an opaque identifier
Active or deactivated flagThe core of the "deactivated account still holds access" finding
Account typeSo Atlassian app accounts can be excluded from human-facing figures
The acting administrator's account identifierRecorded against an acknowledgement or resolution, so a review has an author
Administrator-entered note textFree text, whatever the administrator chooses to write

Personal data appears in the app's stored audit results because it appears in the Jira configuration being audited. It is not enriched, not profiled, not combined with any other source, and not used for any purpose other than presenting the audit to the administrator who requested it.

Administrator-entered notes are free text. The documentation tells customers not to put confidential information in them, because they are stored as part of a finding's state and are visible to any Jira administrator on the site.

5. Data storage

All storage is Atlassian-hosted Forge storage. Matify operates no external database, no object store and no backup of customer data.

StoreHolds

maa-drift-chunkThe change list between scans

Tenant isolation

Forge storage is scoped to the installation, so one site's data is not addressable from another site's installation of the app.

The app adds a second guarantee on top of the platform's: nothing is cached in module scope. Forge may reuse a running container between invocations, so a tenant-derived value held outside a single request would risk crossing installations. Every read goes to storage on every request instead.

6. Data residency

Access Auditor stores data only in Atlassian-hosted Forge storage, which follows the data residency configuration of the Jira Cloud site it is installed in.

Because the app never moves data out of Atlassian's platform, there is no second location for residency to apply to and no mechanism by which data could be moved to another region. Residency is therefore inherited from your site rather than configured separately in the app.

7. External data egress

No app data is transmitted to Matify, to any analytics provider, or to any other external service.

This is enforced by the platform, not merely intended:

ControlEvidence in the shipped app
No egress permission declaredmanifest.yml contains no permissions.external block — no fetch, images, scripts, styles or frames. Forge blocks any outbound request that is not declared, so an undeclared request cannot occur at runtime even by accident.
No remotesThe manifest declares no remotes entry, so there is no external service the app is permitted to address.
No web triggersThe app exposes no webTrigger module, so there is no unauthenticated inbound URL either.
No third-party backend dependenciesThe backend's runtime dependencies are @forge/api, @forge/events, @forge/kvs and @forge/resolver — all first-party Atlassian packages. No analytics SDK, no error-reporting service, no telemetry library.
No external assets in the interfaceThe Custom UI is bundled and served from the app's own resources. It loads no font, script, stylesheet or image from a third-party host, so no administrator's browser contacts a non-Atlassian domain on the app's behalf.
No outbound emailThe app sends no mail. The support address appears only as text for an administrator to use.

There is no telemetry, no usage analytics, no crash reporting and no product instrumentation of any kind.

8. Permissions and scopes

Read-only by construction

The app declares zero write scopes, zero administration scopes and zero manage:* scopes, and issues only HTTP GET requests against the Jira Cloud REST API. It never creates, edits or deletes a permission scheme, project, group, user, filter or dashboard. The only things it writes are its own audit results, to Forge storage.

Authorisation

Every screen and every action proves the caller holds the Jira ADMINISTER global permission before anything is read or returned. The app asks Jira with the caller's own credentials (asUser() against GET /rest/api/3/mypermissions). Jira, not the app, makes that decision. Only afterwards does the app read configuration with its own app-level credentials.

Background paths — the scheduled trigger, the install lifecycle trigger and the asynchronous scan worker — have no user context at all; on the Forge platform asUser() fails there with AUTH_TYPE_UNAVAILABLE. Those paths therefore never attempt a per-user check and do only what the installation itself consented to.

Every declared scope

Twenty-two in total, and none of them is withheld from this list. Jira Cloud's granular scopes are cumulative rather than alternatives, so some are required only because Jira bundles them into an operation the audit needs.

9. Data retention

WhatRetention
Permission, project and group membership snapshotThe most recent scan only. The previous generation is pruned.
Findings, change history and scan historyThe configured retention period. Default 90 days; selectable as 30, 90, 180 or 365.
Comparison fingerprintsTwo generations, because only the previous scan is ever compared against
Acknowledgement and resolution decisions, and notesUntil an administrator changes them, or until the configured acknowledgement expiry elapses
SettingsUntil an administrator changes them

Pruning runs automatically after each successful scan. A failed scan never triggers deletion, so a bad scan cannot silently destroy audit history.

Deleting everything

Two routes, both complete:

  • Settings → Danger zone → Delete all Access Auditor data. Removes every

scan, finding, change record and acknowledgement stored for the site. The screen shows a count of exactly what is stored before the administrator confirms, and the request is rejected unless it carries a literal DELETE confirmation, so a mis-wired interface or a replayed request cannot trigger it. The app stays installed and scans again afterwards. Nothing in Jira is touched.

  • Uninstalling the app. Forge removes all of the app's storage for the site

as part of uninstallation — snapshot data, findings, change history, acknowledgements and settings are deleted, not hidden.

10. Personal data requests

Because Access Auditor stores Atlassian account identifiers, it implements Atlassian's Personal Data Reporting API.

Once a week the app reports every account identifier it holds to Atlassian, in batches, and acts on Atlassian's answer for each account:

Atlassian's answerWhat the app does
The account was updatedQueues a scan, so the stored display name is refreshed from Jira rather than left stale
The account was closedDeletes that account's finding-state records individually, then purges the stored audit data and rebuilds it by scanning, so a closed account does not survive inside an old snapshot. The site's settings and exclusion lists are kept.

This cycle runs whether or not the site's licence is active. The scheduled trigger deliberately carries no licence filter: erasing data about someone who has left is an obligation that does not lapse with a subscription.

The report is a call between the app and the Atlassian platform. No data reaches Matify or any third party through it.

A customer who needs data removed sooner than the weekly cycle can use either deletion route in section 9, both of which are immediate.

11. Logging

The app writes operational log lines to the Forge platform log. They record counts, durations, HTTP status codes, error codes and reasons — and nothing that identifies a person, a project or a group.

Concretely, the complete set of logged events is: a scan starting, being skipped with a reason, completing with its counts and duration, or failing; expired acknowledgements as a count; a scan being queued; an install lifecycle event as a type; the personal data report with its counts; and app data being deleted with its counts.

Never written to a log: account identifiers, display names, project keys, project names, group names, permission holders, note text, or any Jira content. Error messages that reach a log are truncated before they are written.

A support investigation into this app never requires reading customer data out of a log line. The diagnostic report an administrator can copy from the Diagnostics tab is built to the same rule.

12. Encryption and transport security

Access Auditor adds no transport of its own, so it inherits Atlassian's:

  • The administration interface is served by Atlassian over HTTPS.
  • All communication with the Jira Cloud REST API goes through the Forge platform

over HTTPS.

  • All data at rest is held in Atlassian-hosted Forge storage and is subject to

Atlassian's encryption-at-rest controls for that storage.

Because there is no external egress, no self-hosted endpoint and no Matify-held credential, the app introduces no additional transport path that would need to be secured separately. Atlassian's own platform documentation is the authority for the specifics of its encryption implementation; Matify does not restate them here as though they were its own controls.

Secrets

The app holds no secrets. No API token, no OAuth client secret, no external credential of any kind, because it talks to no external service. Nothing is stored using Forge's secret storage. No credential appears in the source, the manifest, the interface bundle, the logs, the documentation or the Marketplace listing.

13. External services and subprocessors

None.

Access Auditor uses no external service, and Matify engages no subprocessor for customer data, because no customer data ever reaches Matify. There is no analytics provider, no error-reporting service, no hosting provider besides Atlassian, no content delivery network and no third-party API.

The only party that processes data on the customer's behalf in connection with this app is Atlassian, as the operator of the Jira Cloud site and of the Forge platform on which the app runs. The customer's existing agreement with Atlassian governs that relationship.

14. Compliance posture, stated plainly

Matify holds no SOC 2 report, no ISO 27001 certificate and no other third-party security certification, and this document does not claim one. What it offers instead is a set of properties that can be checked rather than taken on trust:

  • The read-only claim is checkable in the manifest: count the write scopes.
  • The no-egress claim is checkable in the manifest: there is no external block,

and Forge enforces its absence.

  • The storage claim is checkable in the manifest: every entity store is declared

there.

  • Data residency is inherited from your own Jira site, which you control.

Access Auditor is a tool that supports an access review. It is not itself a compliance guarantee, and it is described that way in its documentation.
