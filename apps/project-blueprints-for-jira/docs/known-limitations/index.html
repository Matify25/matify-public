Known limitations

What Project Blueprints doesn't do, or does only partly, and why. Most limits come from what Jira's public REST APIs let an app do. The blueprint's fidelity report, the requester's gallery card and the approval preview show the ones that apply before anything is created.

Not created or copied

  • Board and board configuration (columns, swimlanes, quick filters) and filters are not created or copied. Reason: the app doesn't request Jira's board scopes. Workaround: set up the board in Jira after the project is created.
  • Dashboards and automation rules are not copied. Reason: no suitable API for copying them per project. Workaround: set them up in Jira, or use automation rules scoped to several projects.
  • Work items, attachments and comments are not copied. Project Blueprints sets up empty projects.
  • Priority scheme is not applied. Reason: Jira's priority-scheme API is experimental. The fidelity report lists it under "Won't apply". Workaround: associate it in Jira.
  • Team-managed configuration (work types, fields, workflow, board of a team-managed project) is not copied. Reason: Jira has no API for it. Workaround: a team-managed blueprint creates the project from Jira's built-in Kanban or Scrum template with lead, Administrator role members and governance properties; the team configures the rest.
  • Version dates are not copied. Versions are created unreleased, with name and description.

Not applied or skipped

  • Multi-context fields: a custom field with more than one non-global context for the reference project is captured but not applied. Reason: Jira's assign API accepts one context per field and project. Workaround: assign the context in Jira.
  • Locked fields (Jira-managed fields such as the "Category" field of business projects) and global contexts are skipped. Global contexts already apply to every project.
  • The Jira-managed role atlassian-addons-project-access and app accounts are not copied. Reason: Jira manages them itself.
  • Deactivated or closed accounts in a blueprint are skipped with a note in the preview and in verification.
  • Project properties are copied only if an admin selected them. Keys that Jira or other apps add are not pre-selected.

Not supported

  • Service projects (Jira Service Management) can't be blueprints and can't be provisioned; portal settings and request types aren't covered. They are catalogued only.
  • Jira Product Discovery and customer service projects are catalogued only, not provisioned.
  • Team-managed projects can't be captured as blueprints (see above).
  • Archived projects can't be captured as blueprints.

Behaviour to be aware of

  • Detect, don't block. Jira has no pre-create hook, so the app can't prevent projects created directly in Jira. It detects them and flags them as "Outside the gate". Detection can lag by a few minutes, because the app re-reads a project about a minute after its event and Atlassian may deliver project events late, and the creator shows as unknown when Jira's audit log doesn't name one.
  • Jira's audit log shows the app as the creator of projects made through it. The ledger, the project's provenance property and the Governance page show the people who requested and approved.
  • Shared schemes. New projects share the blueprint's schemes; changes to a shared scheme affect all projects using it.
  • The app user is admin-equivalent. Creating company-managed projects requires Administer Jira, so Jira gives the app user Administer Jira, Administer projects and Bulk change. Jira's global permission settings can't narrow that; the app's own gate does (see Permissions and security).
  • No e-mail. The app sends no e-mail. Notifications go through optional tracking work items in one project you choose.
  • Tracking work items can be blocked. Jira data security policies can block app access to work items. Tracking is then skipped and the failure is recorded; the request isn't blocked.
  • Retry window. Remaining steps of a partial request can be retried within 7 days of the approval. After that, leave the project as is or submit a new request.
  • Blocked requests can't be resumed or re-approved. The requester submits a new request.
  • Free text (purpose, metadata values, reject reasons, review notes) isn't scanned for personal data. A Jira admin can redact a request's free text afterwards (see the Admin guide).
  • Project properties are visible. The app's properties com.matify.pbj.provenance and com.matify.pbj.governance can be read by everyone with Browse Projects on the project and changed by its project admins, like any Jira project property. The app keeps its own records as the authority.
  • Permission changes reach read views within 5 minutes. Admin read views and the request form cache permission checks for up to 5 minutes; actions that change requests, blueprints, policies, settings or the catalog check at once.
  • Key check timing. In the request form, the key and name check answers about 1 to 1.5 seconds after you stop typing (it waits 0.4 seconds, then asks Jira through Atlassian's platform).
  • Catalog filter on very large sites. With about 10,000 projects loaded, the text filter shows its results in about 1 to 1.2 seconds.

Platform

  • Field schemes: Jira's field-scheme APIs are experimental. On sites not yet migrated to field schemes, the legacy field configuration scheme is used instead. Once a blueprint has been captured, Health shows which mode your site uses.
  • Multiple contexts per project: Jira's newer support for several contexts of one field per project hasn't been tested live with Project Blueprints.
  • Rate limits: on large sites the first catalog scan is throttled to an hourly budget and can take hours; provisioning has priority. See Large sites.
  • Catalog page size: the Catalog page holds up to 10,000 projects in the browser at once; use filters on larger sites.
  • Accessibility: the interface is built with Atlassian Design System components. No accessibility conformance is claimed.

Uninstall

On uninstall, a provisioning in progress stops, so that project may be partially set up. Stored data is retained and deleted under Atlassian's Forge data lifecycle for uninstalled apps; a reinstall starts with empty app storage, and the old data can be re-linked only on a request made within 21 days of the uninstall. Export evidence first. Projects and everything the app wrote into Jira stay.
