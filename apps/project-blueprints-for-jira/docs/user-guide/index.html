User guide

This guide explains the concepts behind Project Blueprints and every page of the app. Step-by-step admin tasks are in the Admin guide; the requester's and owner's view is in the Requester and owner guide.

Concepts

Blueprints

A blueprint describes how a new project (space) is set up.

  • A company-managed blueprint is captured from a company-managed software or business reference project. It records the project type, category and default assignee; the seven scheme associations (permission, notification, issue security, work type, work type screen, workflow and field scheme — or the field configuration scheme on sites not yet migrated to field schemes); project roles with their users and groups; components; versions; the project properties you select; and project-scoped custom-field contexts.
  • A team-managed blueprint starts from Jira's built-in Kanban or Scrum template. It applies only the project lead (who becomes the project's Administrator) and the app's own governance properties. Jira has no API to copy a team-managed project's configuration.

New projects share the blueprint's schemes, like Jira's "share settings" option. The app never copies, edits or deletes a scheme. A change to a shared scheme affects every project that uses it, as it always does in Jira.

A blueprint has a status: Draft → Active → Archived. Only active blueprints can be requested. Re-capture reads the reference project again and creates a new blueprint version if the configuration changed. Requests that were already submitted stay pinned to the version they were submitted against.

An open request reserves its key: two open requests can't use the same key. Rejected, withdrawn, expired and cancelled requests release the key.

Approvals

Only users with Administer Jira can approve. Their permission is checked fresh at the moment of approval.

  • Four-eyes: a requester can't approve their own request. Exceptions: the self-approval setting (off by default) and the one-time guided test.
  • Second approval: a blueprint can require two approvals; the second must come from a different Jira admin.
  • Lead confirmation: if the project lead isn't the requester, the approver confirms that this person becomes project lead (project administrator).
  • Exact preview: the approver sees exactly what will be created. If anything changed since the preview, the approval is refused as stale and a new preview is shown.
  • One decision at a time: two admins can't decide on the same request at once.

Provisioning steps

After approval, the app works through a fixed sequence of steps in the background, one request at a time per site:

Create projectCreates the project with every scheme association, lead and category in one call
Record provenanceWrites the project property com.matify.pbj.provenance (request, blueprint, requester, approvers)
Add role membersAdds the blueprint's users and groups to the project roles

Create component / Create versionOne step per component and version
Assign field contextAssigns project-scoped field contexts
Write project propertyCopies the properties selected in the blueprint
Write owner and review dateWrites com.matify.pbj.governance
Update tracking work itemOnly if tracking work items are on
Verify against blueprintRe-reads the project and compares it with the plan
Add to catalogAdds the project to the catalog with origin Governed

Every step is recorded. Steps are retried automatically when Jira rate-limits or returns a server error. Before it repeats a create or add whose outcome is unknown, the app reads Jira first. If creating the project times out, the app looks the key up and continues only when its own records (and the project's name, lead and schemes) show that the app created that project; otherwise the request fails and that project isn't touched.

Owners and reviews

Every governed project gets an owner and a review date (today plus the blueprint's review interval). When a review comes up, the owner confirms under My projects that the project is still needed, recommends archiving, or proposes a new owner. The app never archives or deletes a project; admins decide in Jira.

The ledger

The ledger is an append-only, hash-chained record. Each entry's hash covers the previous entry's hash and the entry's sequence number, time, type, request, project and blueprint IDs, its details and a pseudonymous reference to the actor, so changing or removing any of these breaks the chain (Verify integrity checks it). The readable summary, the project key and the actor's account ID are shown with the entry but are not part of the hash; the account ID is removed when Atlassian reports the account as closed, without breaking the chain. It records requests, approvals (each approver), rejections, expiries, the start of provisioning, the project creation, failed steps and the result, verification, cancellations, resumes, changes to blueprints, policies and settings, the kill switch, owner changes, reviews, projects detected outside the gate, free-text redactions, tombstones for closed accounts and the uninstall. Each provisioning step is listed on the request page.

Jira's own audit log names only the app as the creator of a project, because the app creates projects in the background. The ledger and the project's provenance property record the people who requested and approved it.

Requester pages (Apps → Project Blueprints)

These pages are in Jira's top navigation under Apps → Project Blueprints. Every Jira user can open them; what they can do depends on their permissions.

Request a project

Three input steps: Blueprint → Details → Review, then Submitted. The blueprint gallery shows only active blueprints the requester may use (a blueprint can be limited to certain groups), with "You'll get", "Won't apply" and how many approvals are needed. If requests aren't open, the requester lacks the permission, the licence is inactive or the kill switch is on, the page explains that instead.

My requests

The requester's own requests with status, progress, a link to the new project and the tracking work item (if enabled). Opening a request shows its timeline, provisioning steps and the verification table. Withdraw works while the request is pending. Request similar starts a new request pre-filled from this one (except the key and category).

My projects

Projects the user owns, with review date, review status, last review, last activity, origin and flags, and the actions Still needed, Recommend archive and Transfer ownership….

Admin pages (Jira settings → Apps → Project Blueprints)

Overview

The Get started checklist (until done), key figures (pending approvals, provisioned this month, created outside the gate in the last 30 days, reviews overdue, projects without owner), Needs attention (up to 10 items with one action each), projects created outside the gate in the last 30 and 90 days, projects provisioned per month, and recent activity.

Approvals

Tabs Pending, Waiting for 2nd approval, In progress and History, with a filter by key, name or blueprint. A request page shows the requester's details and the policy result at submission, the grouped plan (Project, Schemes, Roles & members, Components, Versions, Field contexts, Properties, warnings, skipped items and all steps in order), the timeline and the decision panel: Approve and create {KEY}, Reject… and Cancel request. After approval it shows live progress, the step list, the verification table and, where they apply, Stop after current step, Retry remaining {n} steps for {KEY} and Leave as is and close.

Blueprints

The list of blueprints with reference project, type, status, capture state, version, approvals, request and provisioning counts and warnings. Capture from project and New team-managed blueprint create new ones. The editor has the tabs General, Requesters & approvals, Naming & metadata, Roles, Components & versions, Fields & properties and Fidelity report, and the actions Activate, Archive, Re-validate (checks that the referenced schemes, role members, category and field contexts still exist), Re-capture (company-managed blueprints), Export JSON and Delete (only draft or archived blueprints that no request uses).

Policies

Naming & key policies and metadata forms, each with a live tester (Try a key and name). A blueprint references at most one of each.

Catalog

Every project on the site, with filters (key or name, origin, flags, type, style, category, owner, review, inactivity, blueprint; sort by key, name, last activity or review date). The catalog loads 100 rows at a time, up to 10,000 in the browser. Select rows for the bulk actions Assign owner, Set review date, Mark reviewed and Set blueprint reference. A row opens a panel with the project's details, provenance, reviews (with Confirm new owner for pending transfers), timeline, links to Jira and Re-read from Jira. Export CSV (current filter) exports what the filter shows.

Ledger

The ledger, newest first, filterable by type, request ID, project ID and actor. Verify integrity re-checks the whole chain. The Exports section holds the ledger, request, review and evidence exports.

Project settings → Governance

For project administrators (Administer projects on that project) and Jira admins. It shows the project's provenance (requested by, approved by, blueprint, approval and creation date, request ID), or its origin if it wasn't created through the app; its owner, review date, review status, last review and flags; and Request owner change, which a Jira admin then confirms in the app.

Licensing

While the licence is inactive, the app is read-only: no new requests, approvals, provisioning or scans, and no changes to blueprints, policies or settings (open requests can still be withdrawn or cancelled); catalog, requests, ledger and exports stay readable. See README.
